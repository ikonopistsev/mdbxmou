# Code Style

`mdbxmou` использует минимальный системный C++ в стиле Boost/STL и обычные
соглашения Node.js на JavaScript-границе. Цель - короткий прозрачный код с
явным владением и понятным lifecycle native resources.

## C++

- Имена типов, функций, методов, локальных переменных и констант писать в
  `snake_case`.
- Использовать `struct` для простых value/meta/POD-типов. Их поля не имеют
  завершающего `_`.
- Использовать `class` для логики, RAII, владения и инвариантов. Поля классов
  имеют завершающий `_`.
- Отмечать классы `final`, если наследование не предусмотрено.
- Предпочитать короткие технические имена. Не добавлять `manager`, `provider`,
  `service` или `factory` без архитектурной необходимости.
- Всегда указывать namespace явно: `std::vector`, `std::string_view`,
  `std::uint64_t`. Не добавлять новые `using namespace`.
- Узкий локальный alias допустим внутри функции для длинного namespace.
- Использовать `std::string_view`, `constexpr`, `[[nodiscard]]`, `noexcept` и
  brace initialization там, где они упрощают контракт.
- Избегать `std::ostringstream`, если потоковое форматирование не требуется.
  Простые строки собирать через `std::string`, `operator+=` и
  `std::to_string()`:

  ```cpp
  std::string text;
  text += "generation=";
  text += std::to_string(generation);
  ```

  `std::ostringstream` допустим в тестах и редких production error paths, где
  он заметно упрощает диагностику. Не усложнять реализацию ради формального
  отказа от stream: правило применяется рационально.
- Не писать лишние конструкторы для простых структур. Предпочитать defaulted
  constructor, когда он выражает тот же контракт.
- Небольшие helper-функции могут возвращать `auto`, если тип очевиден.
- Избегать template-heavy архитектуры, CRTP и SFINAE без доказанной пользы.
- Не использовать `std::shared_ptr` и `std::weak_ptr` в новом коде. У native
  resource должен быть один явный владелец: обычный объект, `std::unique_ptr`
  либо конкретный N-API finalizer. Non-owning pointers допустимы только при
  зафиксированном lifecycle владельца.
- Исключения допустимы для обработанного, но невосстановимого сбоя. После
  fatal error объект не продолжает работу в частично живом состоянии.
- Использовать `assert` только для невозможных состояний debug-сборки;
  входные и runtime-ошибки проверять явно.
- Предпочитать краткое прямое решение дополнительным уровням абстракции.

## Node.js Boundary

- Публичный JavaScript API использует `camelCase`: `openSync`, `startWrite`.
- C++ wrappers и внутренние методы используют `snake_case`; строковые имена,
  экспортируемые через N-API, сохраняют JavaScript-стиль.
- В JavaScript и TypeScript следовать стилю окружающего файла и не смешивать
  CommonJS/ESM соглашения без необходимости.
- N-API wrapper не должен скрывать lifecycle native resource: `close()` и
  `closeSync()` остаются явными, а ownership не переносится неявно.
- Публичные ошибки и результаты должны оставаться стабильными и пригодными
  для проверки в тестах.

## Decision Comments

- Для неочевидных safety, compatibility и workaround решений оставлять
  короткий комментарий с устойчивым id из `CHANGELOG.md`, например
  `MDBXMOU-0001-S3-M1`. Комментарий объясняет локальный инвариант, а changelog
  хранит причину, воспроизводимый отказ и область изменения.
- Запись, на которую ссылается код, оформлять тремя явными полями: `ID`,
  `Summary` и `Long description`. `Summary` кратко называет решение, а
  `Long description` объясняет исходную проблему, принятое решение и его
  существенные границы.
- Не добавлять такие id к обычной очевидной логике. Если решение можно понять
  непосредственно из кода и оно не защищает исторически важный инвариант,
  комментарий не нужен.

## Formatting

Формат C++ задается [`.clang-format`](.clang-format):

```bash
# Изменить все C++ файлы в src/
node tools/clang-format.mjs

# Изменить только перечисленные файлы
node tools/clang-format.mjs src/envmou.cpp src/envmou.hpp

# Проверить без изменения
node tools/clang-format.mjs --check src/envmou.cpp src/envmou.hpp
```

Без списка файлов команды работают со всем `src/`. Системный `clang-format`
должен быть доступен через `PATH`.

Существующий legacy code не следует массово переформатировать внутри
функциональной задачи. Обязательна проверка новых и измененных C++ файлов;
полная нормализация дерева оформляется отдельной задачей.
